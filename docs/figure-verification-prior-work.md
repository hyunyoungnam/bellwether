# 수치 검증 — 남들은 어디까지 했나 (2026-09-09)

우리가 고안한 것: **에이전트가 진술한 수치에 `⟦도구:인자|수치⟧` 앵커를 달게 하고,
서버가 그 도구를 다시 실행해 모든 숫자를 대조한 뒤 표시한다.**

같은 문제를 다룬 문헌·구현이 실제로 있고, **핵심 아이디어(재계산)는 이미 나와 있다.**
다만 우리 조합은 아직 못 찾았다. 정리하면:

---

## 1. 문제가 실재한다는 근거

| 출처 | 수치 |
|---|---|
| [Numerical Hallucinations in RAG (SIGIR '26)](https://doi.org/10.1145/3805712.3809882) | RAG 실패 500건 분석 — **38.2%가 수치 조작** |
| [Reference hallucinations in commercial agents](https://arxiv.org/html/2604.03173v1) | 인용 환각 11~57% |
| DRACO (프로덕션 질의 100건) | 최고 시스템도 인용 품질 65% |

우리 앵커는 지금까지 *문장*만 막고 있었고, **숫자는 무방비였다**. 저 38.2%가
정확히 그 구멍이다.

## 2. 가장 가까운 선행 연구

### FinGround (2026) — 재계산 + 반올림 허용
[arXiv 2604.23588](https://arxiv.org/pdf/2604.23588). 금융 문서에서 생성된 주장을
원자 단위로 쪼개고, **계산형 주장은 다시 계산한다**: 함축된 수식을 47개 금융 수식
템플릿에서 식별 → 표에서 피연산자 값을 가져와 → **±0.5% 반올림 허용치**로 재계산.

- **같은 점**: 재계산이 검증이라는 전제, 반올림을 명시적으로 다룬다는 점
- **다른 점**: 수식을 *복원*해야 해서 템플릿 라이브러리가 필요하다. 우리는 복원할
  필요가 없다 — **에이전트가 어떤 도구를 어떤 인자로 불렀는지 앵커에 적으므로**,
  서버는 그 도구를 그대로 다시 돌리면 된다. 도메인 수식 템플릿 0개

### TRACER (2026) — 문장 단위 provenance, 그러나 **재실행은 하지 않는다**
[arXiv 2605.09934](https://arxiv.org/html/2605.09934). 멀티모달 도구 에이전트가
**문장마다 provenance 레코드**(도구 turn id + evidence span + 지지 관계)를 함께
생성하게 하고, 검증은 4단계: 스키마 → 도구 turn 존재 확인 → **evidence span이 기록된
도구 출력의 정확한 부분문자열인지** → 관계 타당성(LLM 판정). Traceability 93.6%.

관계를 세 가지로 나눈 것이 우리 상황과 정확히 겹친다:

| TRACER의 관계 | 우리 대응 |
|---|---|
| **Quotation** (도구 출력 거의 그대로) | 우리 인용 앵커 — 부분문자열 검사, 같은 방식 |
| **Compression** (요약) | 우리는 아예 만들지 않음(모델이 문장을 쓰지 않음) |
| **Inference** (여러 증거를 조합한 파생 주장) | **여기서 갈린다**: TRACER는 LLM 판정, 우리는 파생값이 *재계산 가능*할 것을 요구 |

**결정적 차이**: TRACER는 "verification occurs ... **without re-executing tools**" —
기록된 궤적 안에서만 대조한다. 그럴 수밖에 없다. 일반 에이전트의 도구는 웹 검색·OCR
같은 것이라 다시 부르면 다른 답이 온다. **우리는 코퍼스가 고정이라 다시 부를 수
있다.** 이 제품이 원래 갖고 있던 성질(고정 코퍼스)이 그대로 검증 능력이 된다.

### Evidence tracing 서베이 (2026)
[arXiv 2606.04990](https://arxiv.org/html/2606.04990v1). "**provenance gap**" —
에이전트는 도구 궤적과 최종 답변은 보여주지만 **어느 도구 관찰이 어느 주장을
뒷받침하는지는 말하지 않는다"**를 핵심 공백으로 지목. 미해결 문제로 "claim-level
provenance"를 명시한다. 우리 수치 앵커가 정확히 그 claim-level 링크다.

검증 전략을 셋으로 정리: 인용/지지 검사(ALCE, FActScore) · 실행 궤적 점검(TRAIL) ·
정보흐름 강제(FIDES). **재실행 대조는 이 분류에 없다.**

## 3. 인접 계열 — 결론은 대체로 같다

- **data-to-text 수치 충실도**: 생성문에서 숫자를 다시 추출해 원본 레코드와 대조하는
  것이 십 년 된 표준 지표(hallucination rate, content precision). 우리 pool 대조와
  같은 발상. 다만 저쪽은 *평가 지표*, 우리는 *표시 전 게이트*
- **CheckThat! 2025/26 수치 주장 검증**: 자연 발생 수치 주장 검증은 여전히 어려운
  과제로 남아 있고([ClaimIQ](https://arxiv.org/pdf/2509.11492)), 단순 조회 95.6% →
  **다변수 계산은 0%에 가깝게 붕괴**한다는 보고. 즉 *모델에게 검증을 맡기면 실패한다* —
  결정적 재계산이 답이라는 근거
- **deterministic replay** (OrcaReplay, acipta 등 2026 상용화): 업계 표준은
  **replay**(기록 재생)이고 문헌은 **replay ≠ re-execution**을 명시적으로 구분한다
  ("execution is effectful ... replay is a pure analytical operation"). 우리는 부작용
  없는 읽기 전용 도구라 진짜 re-execution이 가능한 드문 경우
- **Guardrails AI 검증기들**(provenance_embeddings / provenance_llm / wiki_provenance):
  전부 임베딩 유사도나 LLM 판정. 결정적 대조는 없음

## 4. 그래서 우리 위치

| | 기록 대조 | 모델 판정 | **재실행 대조** |
|---|---|---|---|
| 인용문 | TRACER, ALCE | Guardrails, FActScore | — |
| 수치 | data-to-text 지표 | CheckThat 계열(붕괴) | **FinGround(수식 복원), 우리(도구 재실행)** |

우리 조합의 고유한 부분은 **"에이전트가 도구 호출을 앵커로 선언 → 서버가 같은 호출을
재실행 → 숫자 대조"** 이고, 이게 가능한 이유는 순전히 **코퍼스가 움직이지 않기
때문**이다. 남들이 이 길을 안 간 게 아니라, 대부분의 에이전트는 갈 수가 없다.

## 5. 문헌에서 가져온 설계 교정 두 개

1. **반올림 허용치를 명시하라** (FinGround ±0.5%). 우리는 다른 규칙을 택했다 —
   **주장의 자릿수가 허용치**(4.4는 4.43을 받고, 1.15는 1.2를 안 받는다). 도메인
   상수가 없어 더 낫다고 본다
2. **관계 타입을 라벨하지 말라** (TRACER의 Inference 관계는 LLM 판정이 필요했다).
   우리는 라벨 대신 **재계산 가능성**을 요구한다 — 재계산 안 되면 `na`로 두고 아무
   주장도 하지 않는다. 판정 계층을 만들지 않는 것이 가드레일 1과 맞다

## 6. 아직 안 한 것 (문헌이 가리키는 다음 칸)

- **claim-level 커버리지 지표**: TRACER의 Provenance F1처럼 "수치 진술 중 몇 %가
  앵커를 달았나"를 측정할 수 있다. 지금은 앵커 달린 것의 통과율만 안다
- **작은 정수 우연 일치**: 우리 pool 대조의 약점. 문헌의 대응은 값을 *경로*로
  지정하는 것(어느 필드인지). 필요해지면 `⟦gap_scan:healthcare#benchmarks.named_by|31⟧`
  같은 선택적 경로 문법으로 좁힐 수 있다

## 7. 실측 후기 (2026-09-09, 같은 날 저녁)

앵커를 에이전트에게 요구하는 설계를 실제 답변에서 측정한 결과 **커버리지 38%**.
같은 답변에서 자기가 앵커로 단 4.4·6.2·1.15를 문장 안에 맨숫자로 다시 인쇄한다.
**검증을 작성자의 협조에 의존하면 안 된다**는 것이 실측으로 확인됐다.

그래서 서버가 **앵커 없는 숫자까지 전수 검사**하도록 바꿨다(그 턴이 부른 도구를
재실행 → 값 풀 → 모든 숫자 대조). 맨숫자 45개의 분류:

| | |
|---|---|
| 도구 결과에 그대로 | 38 (84%) |
| 도구 값 두 개의 단순 연산 | 3 (7%) |
| 둘 다 아님 | 4 (9%) — 천 단위 쉼표 파싱 버그 2, 우리 유의수준 상수 1, gid 1 |

**조작은 0건.** 셋을 고친 뒤 새 답변은 30개 중 30개 확인. 이로써 TRACER가 구조적으로
가진 사각지대(선언한 것만 검증됨)를 우리는 갖지 않는다 — 선언 여부와 무관하게 검사한다.

교훈 하나: **임계값을 쓰는 도구는 그 임계값을 출력에 적어야 한다.** field_trend가
`rule: {z_threshold: 2.576, confidence_pct: 99}`를 반환하게 하자 "|z| ≥ 2.576(99%)"
같은 문장이 특례 없이 검증된다. 상수를 코드에 숨기면 그 상수를 인용한 문장은 영원히
검증 불가로 남는다.
